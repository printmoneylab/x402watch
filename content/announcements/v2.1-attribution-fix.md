**Branch:** `main` after Phase 2d completes.

## What changed

The v2.0 4-layer wash filter and 9-label taxonomy worked correctly on the
inputs they were given. v2.1 rebuilds the layer beneath them — the function
that decides which service a given on-chain payment belongs to.

### The bug

`indexer/evm.py` mapped every payment to a service via:

```sql
SELECT LOWER(seller_address) AS addr, MIN(id) AS service_id
FROM services GROUP BY seller_address
```

One seller wallet → one service_id. For any operator running multiple
endpoints under one wallet, every payment collapsed onto the oldest
service they registered.

Concrete impact: KR Crypto operates 11 endpoints. All 11 share the seller
wallet `0xcF9223eCe895258dEa8D288AEBcf846Ab8E342fB`. Every payment was
attributed to `service_id=14391` (`/api/v1/kr-prices`). The other 10
endpoints — `kr-sentiment`, `arbitrage-scanner`, `kimchi-premium`, etc. —
showed `tx_total=0` on the dashboard despite together accounting for
roughly **${total of memory #21 minus kr-prices}** in actual revenue.

The same bug applied to every multi-endpoint operator on the index. Top
20 multi-endpoint sellers (`0x2bb7…`, Google Maps `0x325b…`, Aubrai
`0x44dc…`, etc.) all collapsed to a single service_id each.

### What we tried first

Before settling on v2.1's approach we investigated three external paths:

1. **CDP settlement log API.** Mapped the entire `X402FacilitatorApi`
   surface in `coinbase/cdp-sdk`. It exposes `verify`, `settle`,
   `discovery/resources`, `discovery/merchants`, and resource search —
   **no past settlement log endpoint.** Confirmed against the
   `coinbase/x402` Python facilitator code path. Earlier 401 responses on
   speculative URLs were just default-not-found behaviour.

2. **On-chain calldata parsing.** x402 settles via EIP-3009
   `transferWithAuthorization`. The ABI has no slot for resource URL.
   The mapping exists only in the off-chain X-Payment HTTP header.
   Structurally impossible.

3. **Same-wallet, same-price disambiguation.** Useful as a partial fix
   (an operator's $0.10 endpoint can be distinguished from their $0.001
   endpoint) but still lossy when two endpoints share a price tier.

### What v2.1 ships

A two-layer attribution stack:

**Layer 1 (universal, partial accuracy)** — `evm.py:165` now keys on
`(seller_address, price_amount)` instead of just `seller_address`. KR
Crypto's 11 collapses become 4 (one per price tier). Same-price
collisions within a tier still resolve to the oldest service in that
bucket. Lossy, but no longer collapse-everything-to-one.

**Layer 2 (opt-in, exact accuracy)** — a public **Merchant Feed
Protocol**: any merchant can publish a signed JSON ledger of their own
settled payments at `/.well-known/x402watch-feed.json`. x402watch's
indexer fetches the feed, verifies the Ed25519 signature against a key
the merchant registered out of band, and overwrites the per-payment
`service_id` with the merchant's authoritative mapping. KR Crypto
shipped first; their attribution is now 100% accurate per their own
`stats.jsonl` ledger.

Both layers write an `attribution_source` column on every transaction
row so anyone auditing the data can see exactly which mechanism
produced each row's service_id.

### What you'll see on the dashboard after v2.1 backfill

For KR Crypto specifically:
- `services/14391` (kr-prices) **drops** from `tx_total = 2,451` to its
  real value of `<NUMBER>` (≈ ${number from merchant feed for kr-prices}
  on-chain settlements only — about 1,109 non-x402 USDC transfers
  previously falsely attributed are now marked `legacy_unmatched` and
  excluded).
- The 10 other KR Crypto endpoints **gain** their real tx_total counts.
  `kr-sentiment` resolves to ~${kr-sentiment count}; `arbitrage-scanner`
  to ~${arbitrage count}; etc.
- Re-running v2.0's 4-layer wash detection produces a **new label
  distribution** on each affected service. We publish the diff openly

For other top-20 multi-endpoint sellers (Google Maps, Aubrai, 0x2bb7…
etc.) the Layer 1 fix produces a partial improvement; their actual
distributions depend on how many distinct price tiers they use. None
ship merchant feeds yet (we invite them to).

## Adoption: merchants who want exact attribution

If you operate multiple x402 endpoints under one seller wallet, you can
opt into Layer 2 by:

1. Generating an Ed25519 key pair, publishing the public key out of
   band to x402watch.
2. Adding a JSON endpoint at `https://<your-domain>/.well-known/
   x402watch-feed.json` that lists your own settled payments. Reference
   implementation: `oracle-patches/attribution-v2.1/merchant_feed_kr_crypto.py`
   in this repo.
3. Telling us; we add your `merchant_id` + public key to our registry,
   and our indexer starts fetching hourly.

You retain control: revoke the key any time, change endpoints, change
the feed's window. Your settlement claims are cross-checked against
on-chain transactions to prevent inflation.

## GitHub release notes (v2.1.0)

**Title:** v2.1.0 — attribution layer rebuild + merchant feed protocol

### Summary

v2.0 of the wash filter was algorithmically correct but operated on
collapsed attribution: every payment to a multi-endpoint seller was
mapped to that seller's oldest service_id. v2.1 rebuilds attribution
in two layers — a universal partial fix in `indexer/evm.py` and an
opt-in exact fix via a new Merchant Feed Protocol. All affected
service rows are backfilled.

### What changed

- `indexer/evm.py:165` — `(seller_address, price_amount)` composite
  attribution key replaces `seller_address` alone.
- New `indexer/merchant_feed.py` — Ed25519-verified opt-in ledger
  ingestion. Spec at `oracle-patches/attribution-v2.1/merchant_feed_spec.md`.
- New `transactions.attribution_source` column — every row labels its
  own provenance (`legacy_collapse`, `price_match`, `price_match_lossy`,
  `merchant_feed:<merchant_id>`, `legacy_unmatched`).
- New tables: `merchant_feed_keys`, `merchant_feed_state`.
- `transactions_pre_v21_backup` table preserves the pre-v2.1 state
  indefinitely.

### Merchants supported

- KR Crypto (`merchant_id=kr-crypto`) — full ledger from
  `/.well-known/x402watch-feed.json`. 11 endpoints, all attributed
  exactly.

### Breaking changes

None to the public API contract. Dashboard numbers for affected
services change as the backfill propagates; that's documented openly
in `content/announcements/v2.1-attribution-fix.md`.

### Migrations

Apply order:
1. `oracle-patches/attribution-v2.1/evm_attribution_patch.py --apply`
2. `psql -f oracle-patches/attribution-v2.1/backfill_kr_crypto.sql`
3. Load `kr_crypto_settlements_staging` from KR Crypto's stats.jsonl
   (see commands in the SQL file's §4 comment)
4. Re-run the SQL file to perform the actual UPDATE/INSERT pass.
5. `venv/bin/python -m indexer.derive_global` to re-aggregate service
   stats + buyer labels.

Rollback documented in the SQL file §11.

### Acknowledgments

User-reported via "/services?search=kimchi shows 0 traffic" — the
report that surfaced the attribution bug.
